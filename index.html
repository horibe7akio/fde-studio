01

01 / 現場のレイヤーへ

現場には、
まだ「仕様」がない。

メールで届く注文。Excelへの転記。
担当者しか知らない、例外の扱い。
「確認が遅い」の中に、いくつもの仕事がある。

FDEがすること担当者と仕事をたどり、
誰が、何を見て、何を判断するかを聞く。

ツールの導入からではなく、業務の理解から。
目の前の困りごとを、そのまま仕様にしない。

架空の受注業務を使った模式図です。実際の顧客事例や効果測定ではありません。

02

02 / 業務を、構造に変える

散らばる情報を、
判断できる設計へ。

必要なデータは何か。
どの条件なら、自動で進めてよいか。
例外は、誰に確認してもらうか。

散らばった情報を「入力」「判断」「担当」に整理してみよう。

ここが設計の分かれ目自動化する作業と、人に残す判断を分ける。
これが、システムにするための設計図になる。
03

03 / CONCEPT LAYER — DATA

まず、仕事を
データとして見る。

「注文メール」では、まだ粗すぎる。
注文番号、取引先、金額、納期。
判断に必要な事実を、一つずつ取り出す。

DATA事実を、同じ形で扱えるようにする
FDEの問い何が届けば、次の仕事を始められるか。
欠けたとき、誰が気づけるか。
04

04 / CONCEPT LAYER — DECISION

次に、判断を
分岐として描く。

金額が一致すれば、自動で進める。
一致しなければ、人へ戻す。
暗黙の勘を、条件と例外に分ける。

RULE自動化できる判断と、人に残す判断
FDEの問いどの条件まで機械に任せるか。
間違えたとき、止められるか。
05

05 / CONCEPT LAYER — OWNER

そして、判断に
人と責任を置く。

誰が実行し、誰が確認し、誰が承認するか。
「人が見る」だけでは、仕事は止まる。
判断を返す相手と期限まで、仕組みに含める。

OWNER判断が止まらない責任の輪をつくる
FDEの問い例外は、誰の画面に届くか。
その人は、何を見れば決められるか。
06

06 / 3つの概念を、動くシステムへ

データ・判断・担当が、
システムになる。

注文を取り込み、条件を照合。
例外は人に渡し、確認した結果を登録する。
整理したルールと役割が、そのまま仕組みになる。

架空の注文 / 金額に不一致あり

この注文は、自動登録せず人の確認へ進む設計です。

FDEがすること実装して、例外・誤り・権限を確かめる。
業務担当と試し、使われるまで直す。

このデモは仕組みの説明です。実システムや外部データには接続していません。[1]

07

07 / 定義は、会社ごとに違う

名前より、
ここを見る。

FDEの中身は会社ごとに違う。
「客先常駐と同じでは？」という問いにも、
答えられるのは名前ではなく、担っている中身。

顧客と課題・優先順位を決め、技術判断や試作を進められるか。裁量は会社や契約によって異なります。

つくったものが本番で使われ、業務にどんな変化をもたらしたかまで追うか。人月ではなく成果で契約しているかも、見分けの手がかりになります。

現場の解決を共通部品や製品へ戻せるか。PalantirやLayerXのプロダクト型FDEが重視する循環です。

SI・SES・コンサルにも同様の仕事を担う人がいます。FDEの役割は企業により異なり、職種の優劣ではありません。[1][2][3]

08

08 / もう一度、企業全体を見る

一つの現場から、
企業全体の力へ。

受注現場でつくった接続部品や評価の手順。
共通化できれば、他の部署でも活かせる。
さらに、別の顧客への展開につながることもある。

カメラを引いてみる。一つの現場が、企業のどこにあるか見えてきます。

ここがポイント個別の解決を、繰り返し使える力にする。

プロダクト型FDEが重視する考え方です。個別対応が増えるだけなら、人手への依存は残ります。[2][3][4]
